# PreWatch 추천/취향 분석 알고리즘

## 문서 목적

이 문서는 `StatServiceImpl`과 `TasteProfileServiceImpl`에 흩어져 있는 추천/취향 분석 로직의 의도를 정리한다.

현재 리팩토링 단계에서는 알고리즘의 계산 결과를 바꾸지 않고, 코드를 안전하게 읽고 수정하기 위한 기준으로 사용한다.

## 설계 배경

PreWatch는 충분한 사용자 데이터가 없는 초기 프로젝트이므로 머신러닝 기반 추천 대신 규칙 기반 휴리스틱 알고리즘을 사용한다.

기업 서비스 수준의 추천 모델은 많은 사용자 행동 데이터, 평가 데이터, 검증 지표가 필요하다. 이 프로젝트에서는 그런 표본을 확보할 수 없기 때문에, 사용자가 직접 남긴 평가와 영화별 지표를 바탕으로 설명 가능한 추천 방식을 선택했다.

임계값은 대규모 통계 분석 결과가 아니라, 서비스 초기 단계에서 추천 결과가 지나치게 흔들리지 않도록 정한 보수적 기준이다. 향후 실제 사용자 데이터가 쌓이면 이 값들은 조정 대상이 된다.

## 주요 입력 데이터

- `movies.rating`: 영화의 평균 만족도
- `movies.violence_score_avg`: 영화의 평균 폭력성 점수
- `movie_stats.horror_score_avg`: 영화의 평균 공포성 점수
- `movie_stats.sexual_score_avg`: 영화의 평균 선정성 점수
- `movie_genres`: 영화 장르
- `movies.rated`: 관람 등급
- `user_reviews`: 사용자의 개별 평가
- `user_carts`: 사용자의 찜 목록
- `actors`, `movie_actors`: 배우/감독 기반 취향 분석
- `member.taste_title`, `member.taste_report`, `member.taste_anomaly_score`: 취향 리포트 저장용 회원 정보

## 영화 추천 흐름

영화 상세 페이지의 추천은 기준 영화와 비슷한 특성을 가진 영화를 찾는 방식으로 동작한다.

1. 기준 영화의 장르와 관람 등급을 조회한다.
2. 같은 장르를 하나 이상 가진 영화를 후보로 선택한다.
3. 관람 등급 기준에 맞지 않는 영화는 제외한다.
4. 기준 영화와 후보 영화의 평가 지표 차이를 계산한다.
5. 로그인 사용자는 개인 취향 편차를 반영해 기준 점수를 조정한다.
6. 장르 일치 수가 많고 지표 차이가 작은 영화 순으로 추천한다.

비로그인 사용자는 기준 영화 자체의 평균 지표를 기준으로 추천한다.

로그인 사용자는 사용자의 평가 경향을 반영해 기준 점수를 조정한다. 예를 들어 특정 사용자가 일반 평균보다 폭력성에 민감하게 반응했다면, 추천 기준에서도 그 편차를 반영한다.

## 취향 편차 계산

취향 편차는 사용자가 남긴 평가와 영화/장르 평균값의 차이를 계산해 만든다.

- `작품성`: 사용자의 만족도 점수와 영화 평균 만족도 차이
- `액션`: 사용자의 폭력성 점수와 해당 장르의 평균 폭력성 차이
- `스릴`: 사용자의 공포성 점수와 해당 장르의 평균 공포성 차이
- `감성`: 사용자의 선정성 점수와 해당 장르의 평균 선정성 차이

이 값은 사용자가 일반적인 평가 경향보다 특정 요소에 더 민감한지, 혹은 덜 민감한지를 판단하는 데 사용한다.

예를 들어 `액션` 편차가 높으면 사용자가 폭력성/액션 요소를 평균보다 강하게 받아들이거나 선호한다고 해석한다. `스릴` 편차가 낮으면 공포성이나 긴장감 요소를 평균보다 덜 선호한다고 해석할 수 있다.

## 취향 분석 리포트 흐름

`TasteProfileServiceImpl`은 사용자의 평가 이력과 찜 목록을 바탕으로 취향 리포트를 만든다.

1. 사용자의 평가 데이터가 5개 미만이면 초기 안내 리포트를 반환한다.
2. 사용자의 평가 일관성을 계산한다.
3. 자주 본 장르, 배우, 감독을 찾는다.
4. 높은 점수를 준 배우/감독을 찾는다.
5. 활동 패턴, 선호 연도, 선호 러닝타임을 계산한다.
6. 찜 목록과 평가 목록을 비교해 잠재 욕망 메시지를 만든다.
7. 최종 취향 제목, 키워드, 추천 문구를 생성한다.

취향 리포트는 정확한 심리 분석이 아니라, 사용자의 평가 패턴을 읽기 쉬운 문장으로 바꾸는 해석 레이어다.

## 잠재 욕망 분석

잠재 욕망 분석은 사용자가 실제로 평가한 영화와 찜 목록의 차이를 비교한다.

예를 들어 평가 이력은 안정적인 고평점 영화 위주인데 찜 목록에는 낮은 평점 영화가 많다면, 사용자가 새로운 실패 경험이나 호불호가 갈리는 작품을 탐험하려는 신호로 해석한다.

현재 분석 기준은 다음과 같은 패턴을 본다.

- 낮은 평점 영화에 대한 관심
- 특정 감독 작품의 반복적인 찜
- 평가 이력에는 적지만 찜 목록에는 늘어난 장르
- 호불호가 갈리는 중간 평점 영화
- 배우 세대 변화
- 러닝타임 선호 변화

이 분석은 추천 정확도보다 사용자에게 재미있는 자기 해석 경험을 제공하는 목적이 크다.

## 임계값 기준

현재 프로젝트는 충분한 학습 데이터가 없기 때문에 임계값은 휴리스틱이다.

예:

- 평가 5개 미만: 취향 리포트를 만들기에는 데이터가 부족하다고 판단
- 편차 1.0 이상: 특정 요소에 의미 있는 선호가 있다고 판단
- 편차 1.5 이상: 강한 선호 또는 회피 경향으로 판단
- 찜 목록의 30% 이상: 반복적인 관심 패턴으로 판단
- 찜 목록의 40% 이상: 호불호가 갈리는 영화에 대한 탐험 성향으로 판단

이 값들은 확정된 정답이 아니라 초기 서비스에서 알고리즘을 설명 가능하게 만들기 위한 기준이다. 향후 데이터가 쌓이면 실제 사용자 행동 데이터를 기반으로 조정할 수 있다.

## 현재 구조의 주의점

영화별 집계 점수는 현재 `movies`와 `movie_stats`에 나뉘어 있다.

- `movies.rating`
- `movies.violence_score_avg`
- `movie_stats.horror_score_avg`
- `movie_stats.sexual_score_avg`
- `movie_stats.review_count`

이 값들은 같은 성격의 영화별 집계 데이터이므로 장기적으로는 책임을 정리할 수 있다. 다만 추천 알고리즘이 이 값들에 강하게 의존하고 있으므로, 스키마 변경은 별도 리팩토링 단계에서 진행한다.

## 리팩토링 원칙

- 알고리즘 결과를 바꾸는 수정은 별도 작업으로 분리한다.
- 테이블 구조 변경보다 Repository 조회 책임 정리를 먼저 한다.
- 임계값은 현재 알고리즘의 휴리스틱 기준으로 유지한다.
- 숫자만 바꾸는 형식적 리팩토링은 하지 않는다.
- 추천 결과가 달라질 수 있는 변경은 테스트 데이터로 전후 비교한다.
- 과거 더미 데이터보다 현재 API 입력 흐름을 기준으로 판단한다.

## 다음 리팩토링 후보

1. 추천/취향 분석 흐름을 코드 주석보다 문서 기준으로 먼저 이해한다.
2. 추천 후보 조회 SQL과 취향 분석 SQL이 어떤 알고리즘 단계에 해당하는지 표시한다.
3. 알고리즘 변경 전후를 비교할 수 있는 작은 테스트 데이터를 만든다.
4. Repository 조회 메서드의 역할을 정리하되, 계산 결과는 바꾸지 않는다.
5. 집계 점수 컬럼을 `movies`와 `movie_stats` 중 어디에 둘지 별도 작업으로 검토한다.
